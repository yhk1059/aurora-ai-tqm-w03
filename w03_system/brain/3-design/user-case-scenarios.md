# user-case-scenarios — 유저 케이스 시나리오 (dev-browser)

> 상태: **v1 실행 완료 (2026-11-15)**. UC-01 ~ UC-10을 dev-browser로 실행했고 확인 102건이 모두 통과했다. 관찰과 발견한 점은 맨 아래.
> 목적: [`browser-test-scenarios.md`](browser-test-scenarios.md)(TC-00 ~ TC-07, pytest)는 **시연 순서대로** 눌렀을 때 통과하는지 본다. 이 문서는 그 위에 **사용자가 시연 순서를 벗어날 때**를 더한다: 역할별로 자기 일만 하러 들어온 사람, 잘못 누르는 사람, 설명 없이 처음 들어온 사람, 화면 폭과 긴 입력.
> 방식: **이 문서가 원본이다.** 케이스를 여기에 사람 말로 적으면, dev-browser용 실행 스크립트(`e2e/user-cases/UC-xx.js`)를 이 표에서 만든다. 표와 스크립트가 다르면 표가 맞다.
> 두 테스트의 관계: 둘 다 유지한다. pytest는 시연 3건의 회귀 확인(코드를 고칠 때마다 실행), 유저 케이스는 시연 영상 촬영 전과 화면을 크게 바꾼 뒤에 실행한다.
> 기대 값 출처: [도출: 임시 DB에서 dev-browser로 실행한 결과, 2026-11-15]. 업무 의미와 단계 번호는 [`demo-scenarios.md`](demo-scenarios.md), 규칙은 [`business-model.md`](business-model.md) §5를 따른다.

## 0. 실행 환경

| 항목 | 값 |
|---|---|
| 도구 | dev-browser 1.0.0-rc.4 (Chrome, 화면 없이 실행). 스크립트는 Puppeteer 문법 |
| 대상 | 로컬 서버. 실행기가 임시 DB로 따로 띄운다. `data/w03.sqlite`와 배포본은 건드리지 않는다 |
| AI | 재생 모드(`W03_AI_REPLAY=1`)라 API를 부르지 않는다. 유저 케이스는 AI 버튼을 누르지 않는다 |
| 화면 크기 | 1440 × 900 (UC-09만 폭을 바꾼다) |
| 코드 | `e2e/user-cases/`: `run.sh`(실행기), `lib.js`(공통 도우미), `UC-01.js` ~ `UC-10.js` |

실행 (`w03_system` 폴더에서):
```
(cd frontend && npm run build)
e2e/user-cases/run.sh              # 전체 (약 1분)
e2e/user-cases/run.sh UC-01 UC-06  # 고른 것만
```
- 결과는 한 줄에 하나씩 `통과|실패|관찰  케이스  확인 항목  실제 값`으로 나온다. 실패가 있으면 종료 코드가 0이 아니다.
- 화면 캡처는 `data/e2e/uc/`에 남는다 (git에 올리지 않는 폴더).

**확인의 두 종류**
- **확인:** 합격·불합격을 가른다. 하나라도 틀리면 그 케이스는 실패다.
- **관찰:** 합격·불합격이 아니다. 화면이 실제로 어떻게 동작했는지 적어 두고 사람이 판단한다. 판단이 끝난 것은 아래 "발견한 점"으로 옮긴다.

**공통 확인 (모든 케이스 끝)**: 브라우저 콘솔 오류 없음. `/api/` 4xx·5xx는 일부러 실패시키는 단계의 건수와 같음.

**스크립트를 만드는 규칙**
- 화면 조작은 사람이 보는 글자(버튼 이름, 칸 이름)로 찾는다. 출발 상태 준비와 결과 대조에만 API를 쓴다.
- "다른 사람이 동시에 한 일"은 API 호출로 대신한다 (UC-06).
- 표에 없는 조작을 스크립트에 넣지 않는다. 새 확인이 필요하면 표를 먼저 고친다.

## A. 역할별 사용 흐름

### UC-01. SCM 담당자가 근거를 직접 써서 재공급 계획을 승인한다

- **누가·상황:** SCM 담당자가 처음 들어왔다. 위원회는 이미 회수를 승인했고 계획 v1이 초안이다. 출하 경위 확인은 아직 회신이 없다.
- **출발:** 시연 1의 1-5까지 (`demo1`, `upto=1-5`)

| # | 조작 | 확인 |
|---|---|---|
| 1 | 역할을 `SCM`으로 바꾸고 `사건` 탭을 본다 | 재공급 요청 작업이 `열림`, 담당 SCM으로 보인다. `회신 입력` 버튼은 없다 (남의 일) |
| 2 | `재공급 계획` 탭 | `출하 경위 확인 대기 1건` 띠가 결정 전에 보인다 (R11-1) |
| 3 | `결정 입력` → `승인`만 고름 → 근거에 공백만 넣음 | `판단 근거`에 `출하 경위` = `확인 대기`. 근거가 비었거나 공백뿐이면 실행 버튼이 꺼져 있고 "승인하려면 근거를 적어야 합니다" |
| 4 | 근거를 **자기 말로** 적음(예시를 쓰지 않음), 적용일 07-03 → `승인 결정 실행` | 버튼이 켜지고, 실행 뒤 창이 닫힌다 |
| 5 | 결과 확인, `기록` 탭 | 계획 v1 `확정`. 직접 쓴 근거가 화면에 그대로 보인다. 승인 기록에 R11-1. 재공급 요청 작업 `완료` |

### UC-02. 역할마다 자기 일만 할 수 있다

- **누가·상황:** 세 역할이 같은 사건을 차례로 본다. 배치 2개가 `상신중`이고 위원회 결정을 기다린다.
- **출발:** 시연 3-A 출발 상태 (`demo3a`, 출발 단계만)

| # | 조작 | 확인 |
|---|---|---|
| 1 | `품질 담당자`로 `사건` 탭 | `회신 입력`·`클레임 등록`은 있고 `위원회 결정 입력`은 없다 |
| 2 | `품질위원회`로 바꿈 | `위원회 결정 입력`만 있고 `회신 입력`·`클레임 등록`은 없다 |
| 3 | `SCM`으로 바꿈 → `재공급 계획` 탭 → `사건` 탭 | 결정·회신 버튼이 없다. "재공급 계획이 아직 없습니다". **관찰:** 지금 할 일이 없다는 것이 사건 탭에서 읽히는가 |
| 4 | 화면을 거치지 않고 SCM 이름으로 위원회 결정을 서버에 보냄 | 403 `forbidden`. 기록 수와 배치 상태(`상신중`)가 그대로다 |

### UC-03. 품질 담당자가 예시 없이 회신을 손으로 옮겨 적는다

- **누가·상황:** 영업이 전화로 답을 줬다. 담당자가 `시연용 예시`를 쓰지 않고 문장을 적고 결과를 직접 고른다.
- **출발:** 시연 1의 1-3까지 (`demo1`, `upto=1-3`)

| # | 조작 | 확인 |
|---|---|---|
| 1 | 안내 대상 결정 작업 `회신 입력` → 회신 문장만 적음 | 회신 결과를 고르기 전에는 실행 버튼이 꺼져 있다 |
| 2 | 회신 결과에서 `회수 배치 고객만`을 직접 고름, 적용일 07-02 → `회신 반영 실행` | 선택지에 `회수 배치 고객만`·`관찰·해제 배치 고객 포함`이 있다. 버튼이 켜진다 |
| 3 | 작업 줄 확인 | 작업 `완료`, 결과 "회수 배치 고객만", 적은 문장이 그대로 보인다. **관찰:** 손으로 넣은 회신에 출처 표시가 붙는가 |
| 4 | 끝난 작업에 다시 회신 시도 (화면, 그리고 서버에 직접) | `회신 입력` 버튼이 없다. 서버는 409 "열린 작업이 아니다". 결과가 바뀌지 않는다 |

## B. 잘못된 조작과 예외

### UC-04. 결정 창에서 마음을 바꿔 닫는다

- **누가·상황:** 위원회가 거절 사유를 쓰다가 닫는다. 닫는 방법 세 가지 어느 것도 상태를 바꾸면 안 된다.
- **출발:** 시연 3-A 출발 상태

| # | 조작 | 확인 |
|---|---|---|
| 1 | `위원회 결정 입력` → `거절` → 사유를 적음 → `취소` | 창이 닫힌다. 기록 수·결정 수·배치 상태(`상신중`)가 그대로다 |
| 2 | 창을 다시 연다 | **관찰:** 쓰던 사유가 남아 있는가 |
| 3 | 사유를 다시 적고 창 밖(어두운 배경)을 누름 | 상태가 그대로다. **관찰:** 창이 닫히는가, 쓰던 글이 사라지는가 |
| 4 | 사유를 적고 Esc 키 | 상태가 그대로다. **관찰:** Esc로 닫히는가 |

### UC-05. 날짜를 잘못 넣는다

- **누가·상황:** 담당자가 회신을 반영하면서 적용일을 사건의 현재 날짜(07-02)보다 앞선 날로 넣는다.
- **출발:** 시연 1의 1-3까지

| # | 조작 | 확인 |
|---|---|---|
| 1 | 안내 대상 결정 `회신 입력` → 예시 `회수 배치 고객만` → 적용일 **06-30** → 실행 | 거부된다(422). 작업은 `열림`, 기록 수 그대로. 폼에 이유가 날짜와 함께 보인다 |
| 2 | 같은 폼에서 적용일만 07-02로 고쳐 다시 실행 | 다시 쓰지 않아도 그대로 실행되고 작업이 `완료`된다 |
| 3 | `클레임 등록` 폼을 열고 적용일을 비움 | 기록이 늘지 않는다. **관찰:** 실행 버튼이 꺼지는가 |

### UC-06. 두 사람이 같은 계획을 결정한다

- **누가·상황:** SCM 담당자 A가 결정 창을 열어 근거까지 써 둔 사이, 담당자 B가 먼저 승인한다. A가 늦게 실행한다.
- **출발:** 시연 1의 1-5까지

| # | 조작 | 확인 |
|---|---|---|
| 1 | A: `SCM` → `재공급 계획` → `결정 입력` → `승인` → 근거 입력, 적용일 07-03 (실행하지 않음) | — |
| 2 | B가 먼저 승인 (API 호출로 대신함) | 200 |
| 3 | A: `승인 결정 실행` | 거부된다(409). 창이 닫히지 않고 이유가 보인다. **관찰:** 그 문구가 사용자 말로 읽히는가 |
| 4 | 상태 대조 | 재공급 계획 결정 기록은 1건, 계획은 1개 `확정`, 남은 근거는 B의 것 |
| 5 | A: 창을 닫고 새로고침 → `SCM` → `재공급 계획` | B의 근거가 보이고 `결정 입력` 버튼이 없다 |

### UC-07. 실수로 초기화를 누르거나, 쓰다가 새로고침한다

- **누가·상황:** 진행 중인 사건을 보던 담당자.
- **출발:** 시연 2 출발 상태 (`demo2`, 출발 단계만. 기록 14건)

| # | 조작 | 확인 |
|---|---|---|
| 1 | `초기화` → `빈 상태 (S0, 사건 없음)` → 확인 창에서 `취소` | 확인 창에 "지금 상태와 기록이 모두 지워집니다". 취소 뒤 사건과 기록 14건이 그대로다 |
| 2 | `보도 등록` 폼을 연 채 새로고침 | 사건과 기록이 그대로다. **관찰:** 새로고침 뒤 역할 |
| 3 | 역할을 `SCM`으로 바꾸고 새로고침 | **관찰:** 역할이 유지되는가 |
| 4 | `기록` 탭에서 새로고침 | **관찰:** 탭이 유지되는가 |

## C. 심사자 첫 사용

### UC-08. 설명 없이 들어와 화면 안내와 예시만으로 재공급 승인까지 간다

- **누가·상황:** 심사자가 배포 주소를 처음 연다. 문서를 읽지 않았다. 화면에 보이는 버튼과 `시연용 예시`만 누른다.
- **출발:** 빈 상태 (사건 없음)
- 단계마다 사건 탭 맨 위 `사건 현황`의 문구를 관찰로 남긴다. "다음에 무엇을 누를지"가 글자로 읽히는지 사람이 판단한다.

| # | 조작 | 확인 |
|---|---|---|
| 1 | 첫 화면을 읽고 `이 배치로 사건 열기` | "배치를 골라 사건을 엽니다"와 버튼이 보인다. 사건 `INC-001`이 열린다. **관찰:** `사건을 열면` 안내 문구 |
| 2 | `안건 상신` → `안건 상신 실행` | `안건 상신` 버튼이 보인다. 배치가 `상신중`이 된다. **관찰:** `사건 현황` 문구 |
| 3 | (품질 담당자 화면에서 멈춤) → 역할을 `품질위원회`로 바꿈 → `위원회 결정 입력` → 예시 `승인` → `승인 결정 실행` | `사건 현황`에 "위원회가 판정하는 중"이 보이고 담당자에게는 결정 버튼이 없다. `사건 현황`에 "다음 결정: 품질위원회 … 품질위원회 역할을 고르면 입력할 수 있습니다"가 보인다. 위원회로 바꾸면 버튼과 예시가 보이고 그 안내는 사라진다. 배치 `회수진행` |
| 4 | 역할 `SCM` → `재공급 계획` 탭 → `결정 입력` → 예시 `승인 (출고 조건 충족)` → `승인 결정 실행` | 위원회 화면의 `사건 현황`에 "다음 결정: SCM (… 재공급 계획 탭)"이 보인다. 계획 v1 초안과 `출하 경위 확인 대기` 경고가 보인다. 실행 뒤 `확정`. **관찰:** 위원회 승인 뒤 재공급 계획 탭으로 가라는 표시 |
| 5 | `사건` 탭 | 사건 상태 `복구계획확정`. **관찰:** `사건 현황` 문구, 남은 열린 작업 |

## 새 케이스를 더하는 순서

1. 이 문서에 케이스를 표로 적는다: 누가·상황, 출발 상태, 조작, 확인(합격 기준)과 관찰을 나눠서.
2. Claude에게 "UC-xx 스크립트를 만들어 실행해 줘"라고 요청한다. dev-browser로 그 화면을 먼저 열어 구조를 보고(`page.snapshot`), `lib.js`의 도우미로 `e2e/user-cases/UC-xx.js`를 만든다.
3. `e2e/user-cases/run.sh UC-xx`로 실행한다. 실패하면 먼저 표의 기대가 화면과 다른 것인지, 화면이 틀린 것인지 가른다. 화면이 틀렸으면 고치지 말고 "발견한 점"에 적는다.
4. "실행 결과"에 날짜와 함께 한 줄을 더한다.
