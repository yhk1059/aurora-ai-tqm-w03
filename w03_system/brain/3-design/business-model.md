## 1. 한눈에 보기

```
[원료 로트] ──투입──▶ [배치] ──출하──▶ [고객]
     │                  │  ▲               ▲
     │                  │  └──클레임───────┘
     ▼                  ▼
          [사건]  ◀── 이벤트(클레임·보도·회신·위원회 결과)
            │
            ├─▶ 결정 1: 회수 범위   (품질위원회)
            │        └─ 결과가 상태로 남음 ─┐
            ├─▶ 결정 2: 재공급 순서 (SCM, 영업 확인) ◀─┘
            └─▶ 작업 (확인 요청·고객 안내·재공급 요청·출하 경위 확인)
```

사건 하나가 신호(이벤트)를 모은다. 그 신호로 결정 1을 하고, **결정 1의 결과 상태가 결정 2의 입력이 된다.** 근본 원인 "엇갈린 신호를 결정으로 연결하는 주인이 없다"에 대한 직접 대응이다.

## 2. 핵심 객체

| 객체 | 설명 | 출처 | 주요 속성 |
|---|---|---|---|
| 사건 (Incident) | 품질 문제 한 건. 이번 범위는 `LOT-B-2602-P` 1건 | [시스템] | 사건 ID, 기점 로트, 상태, 담당자(품질팀), 개시일 |
| 원료 로트 (MaterialLot) | 원료 입고 단위 | [원본] `material_lot_master_cv` | 로트 ID, 원료, 공급사, 입고검사 결과 |
| 배치 (Batch) | 생산 단위 = **회수 판단 단위** | [원본] `prod_batch_log_cv` | 배치 ID, 생산일, 생산량, QC 결과, **판정 상태**[시스템] |
| 클레임 (Claim) | 고객 품질 신고 | [원본] `qc_claims_cv` + [모의] 신규 입력 | 클레임 ID, 배치, 고객, 확정 여부, 수량, 접수일 |
| 출하 기록 (Shipment) | 배치→고객 출하 | [원본] `shipment_batch_link_cv` (불완전) | 출하 ID, 배치, 고객, 출하일, 수량 |
| 고객 (Customer) | B2B 고객 | [원본] `m_customer_cv` | 고객 ID, 매출 비중 |
| 고객 영향 (Exposure) | 배치×고객 영향 관계 | [시스템] | 배치, 고객, **근거 유형**(출하기록/클레임만/회신), 상태, 수량 |
| 이벤트 (Event) | 사건에 들어오는 신호 | [원본] + [모의] | 유형, **발생일**, **적용일**, 내용, 출처 |
| 결정 (Decision) | 사람이 내린 결정 | [시스템] + [모의 승인] | 유형(회수 범위/재공급 순서), 결정권자, 결과(승인/조건부/거절), 근거, 시각 |
| 작업 (Task) | 결정·규칙이 만든 후속 작업 | [시스템] | 유형, 담당 부서, 상태, 회신 내용, 연결 객체 |
| 재공급 계획 (ResupplyPlan) | 고객별 재공급 순서·수량 | [시스템] + [가정 A-03, A-04] | 고객, 순위, 수량, 예상 월, 출고 조건 |
| 이력 (AuditLog) | 모든 상태 변경 기록 | [시스템] | 대상, 이전→이후 상태, 원인 이벤트·결정, 시각 |

- 이벤트의 **발생일과 적용일을 따로 기록**한다 (A05 §2). 예: 보도는 06-20에 나왔지만 시스템에는 07-01에 반영됨.

## 4. 상태

### 4-1. 배치 판정 상태
```
정상 ──(로트 공유)──▶ 관찰 ──(출하 후 90일 무클레임)──▶ 정상(해제, 사건에는 계속 묶임)
  ▲                    │
  │                    └─(확정 클레임)─▶ 재계산(R1·R2)
  │
기준초과(미상신) ─▶ 상신중 ─┬─ 승인 ──▶ 회수진행
                            ├─ 조건부 ─▶ 부분회수 ─(물류 회신 후)─▶ 회수진행
                            └─ 거절 ──▶ 조사계속 ─(새 확정 클레임 / 조사 회신)─▶ 재상신 후보 → 상신중
```
- 기준일 초기 상태: 보류 배치 2개 = **기준초과(미상신)** [가정 A-05]. 합격 배치 2개 = 정상 → 사건 개시 시 **관찰**로 전환(R4) → 마지막 출하 후 120·128일 무클레임이므로 **즉시 해제 조건 충족 → 정상**(R6). 해제된 배치도 사건에는 묶여 있어, 늦은 클레임이 오면 R7이 다시 적용된다.

### 4-2. 고객 영향 상태
`확인(출하기록)` / `미확인(클레임만)` → `확인요청중` → `회신확인` 또는 `영향없음`

### 4-3. 작업 상태
`열림` → `회신받음` → `완료` (회신이 오면 시스템이 규칙을 다시 돌린다)

### 4-4. 재공급 계획 상태
`초안` → `영업확인중` → `SCM승인` → `확정`. 입력이 바뀌면(회수 범위·영업 회신) `초안`으로 돌아가 재계산한다.

## 5. 판단 규칙

| ID | 규칙 | 근거 |
|---|---|---|
| R1 | 불량률 = 확정 클레임 수량 합 ÷ **생산 수량**. 출하 기준 값은 참고로 표시 | `calculation_definitions` §1.9, decisions |
| R2 | 회수 대상 = 확정 불량 있음 **AND** 불량률 ≥ 10% → 위원회 안건 생성 | `quality_policy_cv` |
| R3 | 언론 보도는 판정을 바꾸지 않는다. 재검토 기록과 "결론 유지 근거"를 남긴다 | `quality_policy_cv` |
| R4 | **[확장]** 사건 배치의 원료 로트를 쓴 다른 배치 → 사건에 묶고 `관찰` | decisions(필수 확장) |
| R5 | **[확장]** QC `보류` 배치에 출하 기록 있음 → 경고 + 생산·물류에 "출하 경위 확인" 작업 | 인터뷰 1차 |
| R6 | 관찰 해제: **마지막 출하일 기준 90일** 무클레임이면 `정상` (근거와 함께 자동 해제) | 과거 클레임은 모두 첫 출하 후 81일 이내(p95 75일) [도출]. A-07 |
| R6-1 | 재관찰(해제 후 클레임으로 관찰 복귀): **마지막 확정 클레임일 기준 90일** 무클레임이면 해제 | A-12 |
| R7 | 사건에 묶인 배치(관찰·해제 포함)에 확정 클레임 → R1·R2 재계산 | decisions |
| R8 | 클레임 고객이 출하처에 없음 → 고객 영향 `미확인` + 물류 확인 요청 + 해당 고객 회수·재공급 보류 | 범위 규칙 ④, A-02 |
| R9 | 위원회 결과 처리: **승인** → `회수진행` + 고객 안내 후보 제시 + 재공급 요청 / **조건부** → 부분 회수(확인 고객만 먼저, 미확인은 물류 회신 후) / **거절** → 사유 필수 입력 + `조사계속` + 원인 조사 작업 생성. 새 확정 클레임 또는 조사 회신이 오면 재상신 후보 | A-08, A-09 |
| R9-1 | 고객 안내 범위: 시스템은 후보(회수 배치 고객 + 관찰·해제 배치 고객을 구분 표시)만 제시하고, **영업이 확인 작업으로 대상을 결정**한다 | 인터뷰 2차. 부서 영향 지점(영업) |
| R10 | 재공급 순서 = ① 확인 고객 → ② 회수 수량 → ③ 매출 비중. 여유 능력 월 약 1.5만 EA 안에서 배분. 영업 임원 회신이 순서를 바꿀 수 있음 | A-03, A-04 |
| R10-1 | 재공급 대상 고객 중 **수주 전년비가 최근 2개월 연속 −20% 이하**인 고객 → 영업 임원 확인 요청 (원인은 분석하지 않음). 기준일 해당: C-101, C-104 | A-13, 범위 규칙 ④. 원본 `sales_customer_summary_cv.booking_yoy_pct` |
| R10-2 | 출하처가 회신으로 확인됐지만 수량 기록이 없는 고객 → **클레임 수량 합을 최소 회수량**으로 사용하고 하한임을 표시 | A-14 |
| R11 | 재공급 출고 조건 = **다른 원료 로트**(≠ `LOT-B-2602-P`) **AND** 배치 QC `합격` | 인터뷰 1차. 3월 중순 이후 M-B 로트 4개 모두 규격내, PL-02 배치 10개 모두 합격 [원본] |
| R12 | 시스템·AI는 결정을 확정하지 않는다. 결정은 결정권자의 승인으로만 일어난다 | `approval_authority_policy` ("Agent는 경계를 넘는 결정을 자동 확정하지 않고 사람에게 상신") |

## 7. 현재 BPMN에서 바꾸는 것

| 현재 (W03 BPMN) | 바꾼 것 | 이유 |
|---|---|---|
| 시작 = 클레임 접수 | 클레임 + **QC 보류 출하** + 로트 공유 신호로 시작 | 확장 R4·R5. 보류 배치가 클레임 전에 이미 나갔다 |
| 품질팀이 배치·검사자료를 수작업으로 취합 | 시스템이 자동 취합 + 로트 기준으로 범위 확장 | 신호가 흩어진 것이 근본 원인 |
| 위원회 분기: 예 / 아니오 | **승인 / 조건부 / 거절** 3분기 | 본선 회신 유형, 출하처 공백 대응 |
| 의결 후 생산·영업이 수작업 확인 | 결정이 **작업을 자동 생성**하고 상태로 남음 | "의결 전후가 끊긴다"(W03 문제 정의) |
| (없음) | **재공급 순서 결정** 단계 추가 (SCM, 영업 확인) | 결정 2. 원본에 복구 절차 없음 |
| 아니오 → "조사·재검토"로 종료 | 거절 사유 필수 + 조사계속 + 재상신 조건 유지 | BPMN 주석: "보류·재검토 종료 ≠ 후속 의무 종료". 정책: 기준 충족 건을 인과 미확정만으로 지연하면 안 된다 |
| 영업·고객대응이 고객 안내 | 시스템이 안내 후보를 제시하고 **영업이 대상을 결정** | 확정되지 않은 정보로 고객 불안을 키우는 과잉 대응 방지 |

## 8. 온톨로지 층 (B안: 가벼운 온톨로지)

> 결정: `decisions.md` 2026-11-12 "온톨로지 = B안". 형식 온톨로지(OWL/RDF·그래프 DB)는 쓰지 않는다.
> 위 §2~§5의 객체·관계·상태·규칙을 **선언형 정의**로 코드에 두고, 화면과 규칙은 반드시 이 정의를 통해 조회·판단·상태 변경을 한다.

### 8-1. 구성
| 층 | 내용 | 저장 |
|---|---|---|
| 정의 | 객체 유형, 관계 유형, 상태 전이표, 규칙 → 관계 유형 매핑 | 코드의 선언형 정의 (구현 시 위치 결정) |
| 인스턴스 | 객체 테이블 + **관계 테이블 하나**(모든 관계를 한 표에) | SQLite |
| 이력 | 상태 전이·관계 추가/변경 기록 | SQLite (AuditLog) |

### 8-2. 관계 유형
| 관계 | 방향 | 생성 근거 | 기본 출처 |
|---|---|---|---|
| `USED_IN` | 원료 로트 → 배치 | `production_material_consumption_cv` / `input_lot_ids` | [원본] (물량은 쓰지 않음) |
| `CLAIMED_ON` | 클레임 → 배치 | `qc_claims_cv.batch_id` | [원본] / 신규 클레임은 [모의] |
| `CLAIMED_BY` | 클레임 → 고객 | `qc_claims_cv.customer_id` | [원본] / [모의] |
| `SHIPPED_TO` | 배치 → 고객 | SBL 출하 기록, 또는 클레임만 있음(R8), 또는 물류 회신 | [원본] / [도출] / [모의] — **확인 수준**으로 구분 |
| `PART_OF` | 배치 → 사건 | 규칙 R4(로트 공유) 또는 클레임 | [시스템] |
| `TRIGGERS` | 이벤트 → 사건 | 이벤트 입력 | [원본] / [모의] |
| `DECIDES` | 결정 → 사건·배치 | 승인 입력 | [모의 승인] |
| `CREATES` | 결정·규칙 → 작업 | 규칙 실행 | [시스템] |
| `ANSWERS` | 회신 이벤트 → 작업 | 회신 입력 | [모의] |
| `RESUPPLIES` | 재공급 계획 → 고객 | 규칙 R10 | [시스템] + [가정 A-03·A-04] |
| `SOURCED_FROM` | 재공급 계획 → 공급 배치 | 규칙 R11 | [원본] (공급 배치의 로트·QC) |

### 8-3. 관계 한 줄이 가지는 속성
| 속성 | 값 | 목적 |
|---|---|---|
| 출처 | `원본` / `도출` / `가정` / `모의` / `시스템` | 완료 조건 5(원본·가정 구분)를 데이터 구조로 충족 |
| 확인 수준 | `확인` / `불완전` / `미확인` | 출하 기록 공백(클레임 111/165건)을 "관계는 있으나 미확인"으로 표현 |
| 근거 참조 | 원본 파일·행 ID, 또는 이벤트·결정 ID | 원본 행까지 추적 (A05 §1) |
| 적용일 / 기록일 | 날짜 | 발생일과 적용일 분리 (A05 §2) |

- 예: `B-02-2602-01 —SHIPPED_TO→ C-105` = 출처 `도출`, 확인 수준 `미확인`, 근거 `QC-xxxxx`(클레임만). 물류 회신이 오면 확인 수준이 `확인` 또는 관계 삭제(`영향없음`)로 바뀌고, 이력에 남는다.

### 8-4. 규칙은 관계를 따라간다
| 규칙 | 온톨로지 위의 동작 |
|---|---|
| R4 (확장) | 사건 배치 → `USED_IN` 역방향 → 같은 로트 → `USED_IN` → 다른 배치 → `PART_OF` 추가 |
| R5 (확장) | 배치 QC = 보류 AND `SHIPPED_TO` 존재 → 경고 + 작업 |
| R8 | `CLAIMED_BY` 고객 ∉ `SHIPPED_TO(확인)` 고객 → `SHIPPED_TO(미확인)` 생성 + 확인 요청 작업 |
| R9 부분 회수 | 회수 대상 = `SHIPPED_TO` 중 확인 수준 `확인`인 고객만 |
| R10 | 회수 범위의 `SHIPPED_TO` 수량 → 고객별 회수량 → `RESUPPLIES` 순서 |
| 상태 전이 | 정의된 전이표에 있는 전이만 허용. 모든 전이는 원인(이벤트·결정·규칙)과 함께 이력에 기록 |

### 8-5. 실제 사용 사례 (심사 증거로 보여줄 것)
1. **사건 범위 조회:** 로트 1개에서 시작해 배치 4개 → 고객 → 클레임까지 한 번에 따라간다.
2. **확인 수준이 판단을 바꿈:** 미확인 관계(C-105)가 부분 회수 범위에서 빠지고, 회신 후 들어온다.
3. **재판단:** 새 이벤트가 오면 관계를 다시 따라가 판단을 갱신하고, 무엇이 바뀌었는지 이력으로 보인다.
4. **연결망 화면:** 사건 화면에 로트·배치·고객·클레임 연결망을 상태 색깔과 출처 표시로 보여준다.

### 8-6. 범위
- 인스턴스는 **사건 1건에 필요한 객체만** 적재한다 (범위 규칙 ①). 회사 전체 데이터를 넣지 않는다.
- 정의는 일반적으로 써서, 다른 사건(배치)을 입력해도 같은 정의로 돌아가게 한다.
