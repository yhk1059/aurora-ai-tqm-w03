## 작업

`w03_system/backend/core/actions.py`에 **회신 반영, 재공급 계획 결정, 재공급 계획 자동 처리**를 더한다. step 4가 만든 실행기의 검사 순서·트랜잭션·기록 방식·ID 규칙을 그대로 따른다. 실행기를 다시 쓰지 않는다.

### 1. `apply_reply` (실행 역할 `quality_owner`)

입력: `task_id`, `reply_text`(회신 원문), `result`(허용 결과 중 하나), `ai_log_id`(선택), `applied_date`.

전제 조건: 작업이 `열림`. `result`가 그 작업 유형의 허용 결과 목록(`ontology.task_type_def`)에 있음. **`해석 불가`나 목록 밖의 값은 거부한다.** 이유: AI가 정해지지 않은 상태 변경을 만들지 못하게 한다(R12).

공통 효과: 이벤트(유형 `회신`, 내용 = 원문, 출처 `모의`, 발생일·적용일) + `ANSWERS`(이벤트 → 작업) + `TRIGGERS`. 작업에 회신 내용과 결과를 기록한다.

| 작업 유형 | 결과 | 작업 상태 | 대상에 일어나는 일 |
|---|---|---|---|
| 출하 경위 확인 | 경위 확인됨 | `열림 → 회신받음 → 완료` | 없음 (판정은 바꾸지 않는다) |
| | 확인 불가 | `열림` 유지, 기한 = `applied_date` + 7일 | 없음 |
| 출하처 확인 | 출하 확인 | 완료 | `TARGETS` 줄 전부 `확인요청중 → 회신확인`. 수량 = **그 배치·그 고객의 클레임 수량 합**, 수량 근거 `클레임 합(하한)`, 근거 참조 = 이벤트 ID (R10-2, A-14) |
| | 영향없음 | 완료 | 줄 전부 `확인요청중 → 영향없음`. **줄을 지우지 않는다** |
| | 확인 불가 | `열림` 유지, 기한 + 7일 | 확인 수준 그대로 (`확인요청중`) |
| 안내 대상 결정 | 회수 배치 고객만 / 관찰·해제 배치 고객 포함 | 완료 | 작업 속성에 확정된 안내 대상 고객 목록을 기록 (R9-1) |
| 수주 급감 확인 | 순서 유지 | 완료 | 없음 |
| | 우선 공급 요청 | 완료 | 없음 (계획은 아래 자동 처리가 다시 계산한다) |
| 원인 조사 | 원인 확인 | 완료 | `TARGETS` 배치 중 `조사계속`인 것 → `재상신 후보` |
| | 원인 미확인 | `열림` 유지, 기한 + 7일 | 없음 (`조사계속` 유지) |
| 결과 통보 | 확인함 | 완료 | 없음 |

- 작업 상태 전이 `열림 → 회신받음`, `회신받음 → 완료`는 둘 다 `changes`에 남긴다.
- 재공급 요청 작업에는 회신을 반영할 수 없다(허용 결과가 없다) → `precondition`.

### 2. `plan_decision` (실행 역할 `scm`)

입력: `plan_id`, `result`(`승인` / `거절`), `reason`(거절이면 필수), `applied_date`.

전제 조건: 계획 상태가 `초안`. 승인이면 `rules.supply_condition(plan_id)`가 충족(R11). **열린 수주 급감 확인 작업이 있어도 승인할 수 있다** (경고는 `rules.warnings`의 `open_sales_check`가 보인다).

효과:
- 결정 생성(유형 `재공급 순서`, 결정권자 SCM, 결과, 근거, 적용일, 출처 `모의`) + `DECIDES`(결정 → 계획).
- 승인 → 계획 `초안 → 확정`. 거절 → `초안 → 기각` + 결과 통보 작업(담당 영업 임원, `TARGETS` = 계획).
- 열린 재공급 요청 작업을 `완료`로 바꾼다(자동 완료).

### 3. 재공급 계획 자동 처리

step 4의 자동 처리 연쇄에 아래를 더한다. 사람 액션이 끝난 뒤, 판정 자동 처리 다음에 돈다.

**`재공급 계획 재계산`**
1. `rules.resupply_lines(conn, today)`를 계산한다. 줄이 없으면(회수 대상 고객 없음) 아무것도 하지 않는다.
2. **가장 최근 버전**(상태와 무관, `기각`·`대체됨` 포함)의 줄과 비교한다. 비교 기준은 (고객, 순위, 수량)이고 예상 월은 비교하지 않는다.
3. 계획이 없거나 줄이 다르면 **새 버전**을 만든다:
   - 계획 객체: 버전 = 이전 + 1, 상태 `초안`, 재계산 원인(이 변화를 일으킨 결정·이벤트 ID와 규칙), 출고 조건 문구(R11), 월 여유 능력 값과 계산 근거(출처 `가정 A-04`).
   - `PLAN_FOR`(계획 → 사건). 줄 객체마다 `LINE_OF`(줄 → 계획), `RESUPPLIES`(줄 → 고객, 출처 `시스템` + 가정 A-03·A-04 표시).
   - 공급 배치: `loader.latest_supply_batch(제품, 기점 로트들)`의 배치를 객체로 싣고(사건에 `PART_OF`로 묶지 않는다) `SOURCED_FROM`(계획 → 공급 배치, 출처 `원본`).
   - 이전 버전이 `초안`이면 `초안 → 대체됨`. 이전 버전이 `확정`이면 그대로 둔다(유효 계획으로 남는다).
4. 줄이 같으면 아무것도 만들지 않는다.

> **왜 "가장 최근 버전"과 비교하는가:** SCM이 v2를 기각한 뒤에도 입력(영업 임원의 우선 공급 요청)은 그대로다. 유효한 버전(v1)과 비교하면 다음 액션마다 같은 계획이 v3, v4로 다시 만들어진다. 이 규칙을 바꾸지 마라.

**`수주 급감 확인 요청`** — 새 초안이 만들어질 때, 줄에 있는 고객마다 `rules.order_drop_signal`이 참이고 **그 고객을 대상으로 한 수주 급감 확인 작업이 상태와 무관하게 하나도 없으면** 작업을 만든다(담당 영업 임원, `TARGETS` = 고객, 속성에 신호 월·값, R10-1).

**`재공급 요청`** — 새 초안이 만들어질 때, 열린 재공급 요청 작업이 없으면 하나 만든다(담당 SCM, `TARGETS` = 계획).

- 자동 처리마다 `action_log`에 따로 한 줄(실행자 `시스템`, 원인 = 규칙 ID + 앞선 액션 순번).
- 계획과 줄의 ID도 결정적이어야 한다(버전 번호와 순위에서 만든다).

### 4. 버전 비교 (`rules.py`에 함수 하나 추가)

```python

    없으면 바로 앞 버전, 그것도 없으면 빈 목록.
    각 항목: customer_id, rank_before, rank_after, month_before, month_after, delay_months(늦어지면 양수), added(bool)."""
```

`rules.py`의 다른 함수는 고치지 않는다.

### 5. `available_actions` 확장

- `quality_owner`: `apply_reply`(열린 작업 중 허용 결과가 있는 것. 작업마다 ID, 유형, 허용 결과 목록).

## 금지사항

- 기존 계획 버전의 줄이나 상태를 덮어써서 "수정"하지 마라. 이유: 버전끼리 비교해 변경 전후 차이를 보여야 한다(§4-4, 시연 2-5).
- 시스템이 계획을 스스로 `확정`하지 마라. 이유: R12. 확정은 SCM의 `plan_decision`으로만 일어난다.
- 회신 문장(`reply_text`)을 코드에서 해석해 결과를 정하지 마라. 이유: 결과는 사람이 고른 `result` 입력으로만 정해진다. 문장 분류는 AI(step 7)가 초안을 내고 사람이 확정한다.
- C-105의 출하 수량을 추정해 만들지 마라. 이유: A-14. 클레임 수량 합을 하한으로만 쓴다.
